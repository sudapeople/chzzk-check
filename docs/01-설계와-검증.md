# 설계와 검증

치지직 점검을 만들면서 내린 결정과, 실제 방송으로 확인한 내용을 적는다. 2026-11-20 기준.

## 출발점

진행자가 자리를 비우고 안내 화면만 띄워 둔 방송에서, 게임할 때보다 시청자수가 오히려 늘어난 것을 보았다.
느낌이 아니라 기록으로 확인하고, 치지직에 확인을 요청할 자료를 남기는 것이 목표다.

요구 조건은 세 가지였다.

- 특정 채널 하나가 아니라 처음 보는 방송도 바로 점검할 수 있을 것
- 계속 떠 있는 프로세스 없이, 점검하는 순간에만 일할 것
- 명령어가 아니라 눈으로 보는 맥 앱일 것

## 구조

- `src/check.mjs` : 점검과 판정 로직 전부. Node.js 내장 `fetch` 와 `WebSocket` 만 쓰고 추가 패키지가 없다
- `src/ChzzkCheck.swift` : 화면. 번들 안의 `check.mjs --json` 을 실행해 한 줄에 하나씩 나오는 JSON 을 그린다

로직을 한 곳에만 두려고 이렇게 나눴다. 기준값을 고치거나 자체 점검(`selftest`)을 돌릴 때 `check.mjs` 만 보면 되고,
앱 없이 명령줄로도 같은 결과를 얻는다. 대신 Node.js 가 설치되어 있어야 한다.

## 핵심 발견: 지나간 흐름을 되짚는 방법

밖에서는 시청자수의 과거 값을 알 수 없다. 점검한 순간의 값만 얻는다.
그런데 치지직 채팅 서버에 최근 채팅을 요청하면(최대 50개), 채팅마다 그 순간의 채팅방 접속 인원(`memberCount`)이 찍혀 온다.

- 채팅이 뜸한 방송일수록 50개가 몇 시간 전까지 거슬러 올라간다
- 그래서 점검하는 순간에, 그 전 몇 시간 동안 채팅방 인원이 어떻게 변했는지 볼 수 있다
- 채팅이 많은 방송은 몇 초에서 몇 분만 보인다

처음 살펴본 방송에서는 채팅방 인원이 26~28명으로 유지되다가, 채팅이 없던 70분 사이에 45명으로 늘어 있었다.
"자리를 비운 뒤 늘었다"는 관찰과 맞았다.

## 채팅방 접속 인원과 시청자수

채팅방 접속 인원은 시청자수와 다른 값이다. 같은 날 살펴본 방송들에서 채팅방 접속 인원은 시청자수의 1.1~1.9배였고,
30곳을 훑어본 목록의 중앙값은 1.3배였다. 채팅창만 띄운 접속, 방송 도구, 여러 창 등이 함께 잡히기 때문으로 보인다.

그래서 "채팅방 접속 인원이 시청자수의 60% 미만"을 신호로 삼았다. 영상만 받아 가고 채팅방에는 들어오지 않는 접속이 많다는 뜻이기 때문이다.
반대로 시청자가 늘 때 채팅방 인원도 같이 늘었다면, 실제 브라우저로 접속한 쪽에 가깝다. 이 경우 맞시청, 여러 창, 자동 시청,
실제 시청자를 밖에서 구분할 수 없다.

## 시험하다 고친 오판

- 방송을 막 시작한 채널이 "채팅방 인원 급증"으로 잡혔다 (9분 사이 15명에서 68명). 시작 직후에 사람이 몰리는 것은 정상이라, 방송 시작 15분 이내는 판정에서 뺐다
- 채팅이 뜸하면 두 값 사이가 길다. 70분 사이에 늘어난 것을 "급증"이라고 부르면 과장이라, 10분을 넘으면 "크게 증가"로 쓰고 간격과 "정확한 시점은 모름"을 함께 적는다
- 훑어보기에서는 신호가 한 건씩 붙는 방송이 여럿 나온다. 자리 비움 방송, 다시보기를 남기지 않는 채널 등 정상 사례가 대부분이라 신호를 "들여다볼 후보"로만 본다

## 더 강한 근거

한 번의 점검으로는 확정할 수 없다. 근거가 강한 순서는 이렇다.

1. 제3자 기록 : 통계 사이트가 따로 수집한 그 방송의 시청자수 그래프
2. 반복 : 여러 날에 걸쳐 같은 모양이 되풀이되는 것 (방송별 비교, 반복 패턴 보고서)
3. 늘어난 모양 : 한 번에 계단처럼 오르고 그 뒤 전혀 움직이지 않는 것 (지켜보기)
4. 정상적인 사정이 없다는 확인 : 드롭스, 같이보기, 파티, 유료 광고 표시가 없었다는 것 (함께 볼 상황)

신고문 초안은 본 것만 적고 "조작이다"라고 쓰지 않는다. 확인을 요청하는 글이다.

## 리소스 관리

동작 하나가 끝날 때마다 그 동작이 쓴 것을 치운다.

- 점검은 `check.mjs` 를 한 번 실행하고 끝난다. 앱은 프로세스가 끝날 때까지 기다려 거두고, 파이프를 닫고, 참조를 비운다
- 네트워크 요청에는 10초 제한이 있고, 채팅 소켓은 성공·오류·시간 초과(8초) 어느 경로든 닫는다
- 지켜보기는 직접 켰을 때만 돌고, 방송이 끝나거나 12시간이 지나면 스스로 멈춘다. 취소, 목록에서 지우기, 창 닫기, 앱 종료 때 끝낸다
- 앱이 강제 종료되어도 지켜보기 프로세스는 1초마다 부모를 확인해 따라 끝난다
- 목록은 300건, 방송 화면 그림 캐시는 20장까지만 쥐고 있고, "목록 비우기"로 모두 비울 수 있다
- 증거는 앱이 자동으로 지우지 않는다. 설정에서 저장 폴더가 쓰는 용량을 보여 준다

확인한 값 (Apple Silicon, macOS 27.2).

| 상황 | 남은 점검 프로세스 | 앱이 연 파일 수 |
|---|---|---|
| 앱 시작, 점검 1회 뒤 | 0 | 61 |
| 다시 점검 5회 뒤 | 0 | 62 |
| 지켜보기 켬 | 1 | 65 |
| 지켜보기 끔 | 0 | 62 |
| 지켜보는 중 앱 종료 | 0 | - |
| 지켜보는 중 앱 강제 종료 | 0 (스스로 끝남) | - |

## 넣지 않은 것

- 자동 반복 점검, 백그라운드 상주 : 상시 프로세스를 두지 않는다는 조건에 어긋난다
- 클립보드 주소 자동 인식 : 앱을 켤 때마다 macOS 가 붙여넣기 허용을 물을 수 있다
- 채팅 닉네임과 내용 저장 : 판정에 필요하지 않다. 시각과 인원 수, 익명 번호만 남긴다
- 시청자 목록 조회 : 공개되어 있지 않고, 개인을 추적하는 일이 된다
